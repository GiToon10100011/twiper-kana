# 0001. 문제 전환은 確定 후에 한다 (리셋 전략 R4)

- 상태: 채택 (2026-10-17)
- 근거: iPhone 실기 trace `packages/core/test/fixtures/traces/ios-safari-18-kana.json` (iOS 18.7, Safari 탭, 4회차 × 6줄)과 사용자 관찰
- 관련: 설계 문서 §7 UX Flow, §8 Input Capture, §19 Recommended First Implementation

## 배경

조합 중 문자열이 목표와 같아지는 순간 다음 문제로 넘기려면, 조합을 끊고 입력창을 비워야 한다. 이때 키보드를 유지할 수 있는지가 M0의 가장 큰 기술 위험이었다. `/lab/ime`에서 네 가지 리셋 전략을 시험했다.

| 전략 | 방법 |
|---|---|
| R1 | 겹쳐 둔 두 번째 입력창으로 포커스를 옮기고 이전 입력창을 비운다 |
| R2 | 조합 중에 `value = ''`를 대입한다 |
| R3 | `blur()` → 비움 → `focus()` |
| R4 | 조합 중에는 건드리지 않고, 사용자가 確定한 뒤 비운다 |

## 관찰

**1. 플릭 한 번의 이벤트 순서**

```
keydown (keyCode 229, key=입력한 가나)
compositionstart        ← 조합의 첫 글자에서만
compositionupdate       data = 조합 문자열 전체
beforeinput / input     insertCompositionText, 값 = 조합 문자열 전체
keyup
```

플릭마다 조합 문자열 전체가 값으로 들어온다. 이벤트 뒤의 (값, 조합 여부)를 스냅샷으로 넘기는 현재 설계가 그대로 동작한다.

**2. 確定 순간의 이벤트 순서**

```
beforeinput / input     insertCompositionText
beforeinput / input     deleteCompositionText   ← 값이 잠시 ""
beforeinput / input     insertFromComposition   ← 값 복원
compositionend
```

한 태스크 안에서 값이 비었다가 돌아온다. 이벤트를 태스크 단위로 모으는 `task` 모드는 이 순간을 보지 않는다. 이벤트마다 즉시 판정하는 `sync` 모드는 이를 "글자를 지웠다"로 잘못 읽을 수 있다.

**3. 리셋 전략별 결과**

| 전략 | 결과 | 다음 줄 첫 입력까지 (중앙값) |
|---|---|---|
| R1 | 입력이 들어가지 않아 입력창을 다시 터치해야 함 | 4.4초 |
| R2 | 같음 | 4.1초 |
| R3 | 같음 | 5.0초 |
| **R4** | **포커스가 유지돼 바로 이어서 입력** | **1.4초** |

- R1–R3에서도 visualViewport 높이는 418px로 유지됐다. 키보드는 화면에 남아 있었지만 입력창과의 연결이 끊긴 것으로 보인다.
- 시간은 줄 완료부터 다음 줄의 첫 `compositionstart`까지다. 다음 줄을 읽는 시간이 모든 전략에 똑같이 들어 있다. R4는 確定 뒤부터 잰 값이다.
- 사용자 평가: "r4는 확정짓고 넘어가면 그대로 포커스가 유지되어 ux좋았습니다."
- 홈 화면 앱(standalone)에서도 같은 결론이었다 (`ios-standalone-18-kana.json`, 같은 날): 중앙값 R1 2.4초, R2 4.5초, R3 3.8초, **R4 1.4초**.

**4. 그 밖의 확인**

- 문장부호 키의 출력은 전각이다: `、` U+3001, `。` U+3002, `？` U+FF1F, `！` U+FF01. 장음은 `ー` U+30FC.
- `カメラ`처럼 변환이 필요한 줄은 전략과 무관하게 確定 후 판정이 잘 동작했다.
- 2026-10-21 Lv.16 가타카나 실기 확인(사용자 보고): `かめら`를 치면 후보 줄에 `カメラ`가 나오고, 후보를 누르는 즉시 確定되어 다음 단어로 넘어간다. trace의 `~かめら → =カメラ`와 같은 동작이다.

## 결정

1. **모든 단계에서 다음 문제로 넘어가는 것은 確定 후다.** 조합 중에는 입력창을 건드리지 않는다. 確定으로 조합이 끝나면 값을 비우고 다음 문제를 낸다.
2. 설계 문서의 "기초·문자 조합은 조합 중 일치 즉시 정답"은 다음과 같이 바꾼다.
   - 조합 중 문자열이 목표와 같아지는 순간 ✓를 보여 주고, 그 시각을 정답 시각(속도 측정 기준)으로 기록한다. 確定 탭은 속도에 넣지 않는다.
   - 다음 문제로 넘어가는 것은 確定 후다.
3. 입력 어댑터는 `task` 모드만 쓴다.
4. `keydown`의 `key` 값(입력한 가나)은 판정에 쓰지 않는다. 결과 문자열만 본다는 원칙을 지키고, 플랫폼마다 다르기 때문이다.

## M1에 미치는 영향

- core: `InputSession`에 "조합 중 문자열로 진행과 오류를 추적하되, 완료는 確定 후"인 판정을 추가한다. 정답 시각(`matchedAt`)과 완료 시각(`completedAt`)을 나눈다.
- web: 훈련 입력창은 R4만 쓴다. R1용 두 번째 입력창은 만들지 않는다.
- 튜토리얼 Part 0에 "줄을 다 치면 確定 키로 다음 문제"를 안내한다.
