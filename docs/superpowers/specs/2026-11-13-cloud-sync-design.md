# twiper — 기기 간 동기화 설계

> 작성일 2026-11-13 · 상태: **S1 구현 중, 나머지는 설계.** 2026-11-13 사용자 결정: 계정 없이 동기화 코드로 시작, 설정도 동기화, 무료 구성(Vercel Hobby + Neon Free)으로 운영 · 관련: [구현 계획](2026-10-07-twiper-design.md) §13 Storage, §16 M4 「클라우드 동기화 설계 문서」, Future 「계정·크로스 플랫폼 동기화」

## 0. 요약

- **계정 없이 「동기화 코드」로 기기를 묶는다.** 코드 하나를 아는 기기끼리 같은 「동기화 공간」을 쓴다. 이메일·비밀번호·이름을 받지 않는다.
- **서버는 암호문만 보관한다 (종단 간 암호화).** 암호화 키는 코드에서 만들고 서버로 보내지 않는다. 서버는 내용을 읽지도 합치지도 않으며, 기기에서 올린 묶음을 순서대로 쌓아 두었다가 돌려줄 뿐이다.
- **합치기는 기기에서, 지금 백업 가져오기와 같은 규칙으로 한다.** 기록은 늘기만 하고(지우는 기능이 없다), 합치는 규칙이 순서·중복과 무관하므로, 어느 순서로 받아도 모든 기기가 같은 상태에 이른다.
- **설정도 맞춘다.** 설정은 기록과 달리 바뀌는 값이므로, 항목마다 「마지막에 바꾼 기기」가 이긴다 (§4.4).
- **서버 후보는 지금 배포처인 Vercel의 Functions + Postgres(Neon).** 서버 코드는 API 여섯 개다.
- 먼저 고칠 것이 하나 있다. **응시·플레이 횟수는 지금 「큰 쪽」으로 합쳐서, 두 기기의 횟수를 더하지 못한다.** 횟수를 세션 기록에서 다시 세도록 바꾼다 (§4.3).

## 1. 왜 필요한가

| 상황 | 지금 | 동기화 후 |
|---|---|---|
| 같은 iPhone의 Safari 탭과 홈 화면 앱 | **저장소가 따로라 기록이 갈린다.** 백업 파일로만 옮길 수 있다 | 한쪽에서 코드를 복사해 다른 쪽에 붙여 넣으면 이어진다 |
| iPhone과 iPad를 함께 쓴다 | 백업 파일을 iCloud Drive로 옮겨 가져오기 | 자동으로 합쳐진다. 한 기기에서 바꾼 설정(속도 단위 등)도 따라간다 |
| 오래 열지 않아 iOS가 사이트 저장소를 지웠다 (계획 §17 위험 7) | 마지막 백업 이후 기록을 잃는다 | 코드를 다시 넣으면 서버에서 되찾는다 |
| 기기를 바꾼다 | 백업 파일 | 코드 입력 |

백업 파일(설정 › 기록 백업)은 서버가 필요 없는 기본 수단으로 계속 둔다. 동기화는 켜는 사람만 쓰는 선택 기능이다. 계획 §2의 비목표 「로그인 필수」와 충돌하지 않는다.

## 2. 지금 저장 구조 (2026-11-13 기준, 사실)

| 데이터 | 위치 | 모양 | 백업 파일에서 합치는 규칙 |
|---|---|---|---|
| 시도 기록 (줄 하나) | IndexedDB `attempts` | `AttemptRecord`, `id`는 ULID. 한 번 쓰면 바뀌지 않는다 | `id`가 없는 것만 더한다 (`dexieRepo.mergeRecords`) |
| 세션 (한 판) | IndexedDB `sessions` | `SessionRecord`, 끝나면 `endedAt`·`summary`가 채워진다. 레벨은 `L1`…, 종합 테스트는 `test-kana` 등 | 없거나, 지금 것이 끝나지 않았고 들어온 것이 끝났으면 바꾼다 (`replacesSession`) |
| 레벨 진도 | localStorage `twiper.progress.v1` | 레벨별 `clearedAt`·`plays`·`bestAccuracy`·`bestKpm` | `clearedAt`은 이른 쪽, 나머지는 큰 쪽 (`mergeProgress`) |
| 종합 테스트 기록 | localStorage `twiper.exams.v1` | 종목별 `plays`·`best`(가나/분 최고 판)·`romajiBest`(로마자 속도 최고 판) | `plays`는 큰 쪽, 최고 기록은 각각 빠른 쪽 (`mergeExamRecords`) |
| 설정 | localStorage `twiper.settings.v1` | 언어·속도 단위·도움말 시간·한자 채점·전체 해금 | 백업에 넣지 않는다 |
| 기기 표시 | localStorage `twiper.onboarded`, `twiper.examRules.seen` | 튜토리얼·시험 규칙을 봤는지 | 백업에 넣지 않는다 |

오늘 띠·연속 일수·달력·내 실력·추세·약점 연습·오늘 복습은 모두 **시도 기록에서 계산한다**. 따라서 시도 기록만 합치면 이 화면들은 따로 손댈 것 없이 맞춰진다.

계획 §13은 「모든 레코드에 ULID `id`·`updatedAt`·`deviceId`」를 두기로 했지만, 지금 기록에는 `id`만 있다. 기록이 바뀌지 않고 늘기만 하므로 `updatedAt`은 필요 없다. `deviceId`는 §4.3의 횟수 계산과 §4.4의 설정 합치기에만 쓴다.

## 3. 요구사항

1. **오프라인 우선.** 동기화가 꺼져 있거나 인터넷이 없어도 지금과 똑같이 동작한다. 서버가 멈춰도 연습은 계속된다.
2. **수렴.** 기기들이 어느 순서로, 몇 번씩 주고받든 결국 같은 기록에 이른다. 같은 묶음을 두 번 받아도 늘지 않는다.
3. **잃지 않는다.** 합치면서 어느 기기의 기록도 지우지 않는다.
4. **설정도 같다.** 한 기기에서 설정을 바꾸면 다른 기기도 다음 동기화 때 같은 값이 된다.
5. **개인정보 최소.** 계정을 만들지 않는다. 서버 운영자도 연습 내용을 읽을 수 없다.
6. **첫 화면을 무겁게 하지 않는다.** 동기화 코드는 켠 사람에게만, 필요할 때 불러온다 (지금 Dexie를 늦게 불러오는 것과 같다).
7. **싸게.** 무료 한도 안에서 운영할 수 있어야 한다.
8. **iPhone Safari의 제약을 따른다.** 백그라운드 동기화(Background Sync API)가 없으므로, 앱이 열려 있을 때만 동기화한다.

## 4. 설계

### 4.1 동기화 코드와 키

```
코드     = 무작위 16바이트 → Crockford base32 26자, 화면에는 4자씩 끊어 보인다 (예: 7K2Q-…)
spaceId  = HKDF-SHA256(코드, info = "twiper-sync/v1/space") 앞 16바이트     ← 서버 주소에 쓴다
authKey  = HKDF-SHA256(코드, info = "twiper-sync/v1/auth")                  ← 요청마다 보낸다. 서버는 SHA-256만 저장
encKey   = HKDF-SHA256(코드, info = "twiper-sync/v1/enc")  → AES-GCM 256    ← 기기 밖으로 나가지 않는다
```

- 모두 WebCrypto(`crypto.subtle`)로 만든다. iOS Safari에서 쓸 수 있다.
- 코드는 localStorage `twiper.sync.v1`에 둔다. 「코드 보기」에서 다시 확인하고 복사할 수 있다.
- **코드를 잃으면 서버의 기록은 되찾을 수 없다.** 기기에 남은 기록은 그대로이므로, 새 코드를 만들면 그 기기의 기록이 새 공간으로 올라간다. 화면에서 이것을 분명히 알린다.
- QR 코드는 넣지 않는다. iPhone 카메라로 읽으면 홈 화면 앱이 아니라 Safari 탭이 열려, 정작 묶고 싶은 쪽으로 가지 않기 때문이다. **복사 → 붙여 넣기**를 기본으로 한다.

### 4.2 묶음 (batch)

기기가 올리는 단위. 내용은 지금 백업 파일과 같은 모양이며, 서버에는 암호문으로만 간다.

```ts
interface SyncBatch {
  readonly format: 'twiper-sync';
  readonly version: 1;
  readonly deviceId: string;            // 기기마다 한 번 만든 ULID
  readonly progress: Progress;          // 이 기기의 지금 진도 (작아서 매번 통째로)
  readonly exams: ExamRecords;          // 이 기기의 지금 종합 테스트 기록
  readonly legacyPlays: LegacyPlays;    // §4.3
  readonly settings: StampedSettings;   // §4.4. 이 기기가 아는 설정 항목별 값과 바꾼 때 (작아서 매번 통째로)
  readonly attempts: readonly AttemptRecord[];  // 지난번에 올린 뒤 새로 생긴 것만
  readonly sessions: readonly SessionRecord[];  // 지난번에 올린 뒤 새로 생기거나 끝난 것만
}
// 보내는 값 = AES-GCM(encKey, iv, gzip(JSON.stringify(batch)))
```

- 압축은 `CompressionStream('gzip')`을 쓴다 (iOS Safari 16.4부터).
- 「지난번에 올린 뒤」는 Dexie에 `outbox` 저장소를 덧붙여 추적한다 (`version(2)`, 기존 `version(1)`은 지우지 않는다). 연습으로 생긴 기록뿐 아니라 백업 가져오기로 들어온 기록도 outbox에 넣는다. 그렇게 해야 Safari 탭에서 가져온 기록도 공간으로 올라간다.
- 처음 켤 때는 이 기기의 기록 전체를 올린다 (지금 백업 파일 만들기와 같다). 요청 한도(§4.6)를 넘으면 **기록을 나눠 여러 묶음으로 올린다.** 묶음마다 그 자체로 완결된 `SyncBatch`이고 합치기가 합집합이므로, 서버나 기기가 조각을 다시 이어 붙일 필요가 없다.
- 모르는 필드가 있어도 버리지 않고 넘긴다. 새 버전 앱이 더한 필드를 옛 버전이 지우지 않게 하기 위해서다. `version`이 더 높은 묶음을 만나면 **거기서 받기를 멈춘다.** 그 묶음과 뒤의 묶음은 합치지 않고, `lastSeq`도 그 앞 번호까지만 올린다. 「앱을 업데이트하세요」라고 알리고, 업데이트한 뒤 그 묶음부터 다시 받는다.

### 4.3 합치기 규칙과, 먼저 고칠 횟수 문제

받은 묶음은 지금 `restoreBackup`과 같은 길로 합친다.

| 데이터 | 규칙 | 순서·중복과 무관한가 |
|---|---|---|
| 시도 기록 | `id` 합집합 | 그렇다 |
| 세션 | 끝난 것이 끝나지 않은 것을 이긴다 (`replacesSession`) | 그렇다 |
| 처음 끝낸 날 | 이른 쪽 | 그렇다 |
| 최고 정확도·속도, 최고 판 | 큰 쪽 / 빠른 쪽 | 그렇다 |
| **플레이·응시 횟수** | 지금: 큰 쪽 | **아니다.** A 기기 5회와 B 기기 3회를 합치면 8회여야 하는데 5회가 된다 |
| 설정 (항목별) | 바꾼 때가 늦은 쪽, 같으면 `deviceId`가 큰 쪽 (§4.4) | 그렇다 |

**고치는 법: 횟수를 세션 기록에서 다시 센다** (계획 §13 「로그 병합 후 재집계」).

- 레벨 플레이 횟수 = 그 레벨의 끝난 세션 수. 종합 테스트 응시 횟수 = 그 종목(`test-<종목>`)의 끝난 세션 수. 세션은 `id` 합집합이므로 기기 수만큼 정확히 더해진다.
- 단, 세션을 남기기 전의 옛 횟수는 세션이 없다. 그래서 **S1(세션으로 횟수를 세기 시작할 때)에 기기마다 한 번** **`legacyPlays[deviceId] = { 레벨·종목: max(0, 지금 횟수 − 끝난 세션 수) }`** 를 만들어 둔다. 동기화와 상관없이 만들고, 동기화를 켜면 이미 있는 값을 묶음에 실을 뿐이다. 백업 파일에도 싣는다. 구현은 이 값을 **처음 필요할 때**(백업 만들기·가져오기, 동기화) 만든다. 레벨을 칠 때마다 횟수와 끝난 세션이 함께 1씩 늘므로, 언제 만들어도 S1을 넣은 때와 같은 값이다. 각 항목은 그 기기만 쓰므로 부딪히지 않는다.
- **`legacyPlays`가 없는 옛 백업 파일을 가져올 때:** 파일 안에서 레벨·종목마다 `max(0, 파일의 횟수 − 파일의 끝난 세션 수)`를 계산해, 가져오는 기기의 `legacyPlays` 몫에 큰 값으로 합친다. 그래서 옛 횟수가 사라지지 않고, 같은 파일을 두 번 가져와도 늘지 않는다.
- 보이는 횟수 = 끝난 세션 수 + 항목마다 **모든 기기의 `legacyPlays` 가운데 가장 큰 값.**
- **더하지 않고 큰 값을 쓰는 이유:** 같은 백업 파일을 가져온 기기들(예: Safari 탭에서 내보내 홈 화면 앱에서 가져옴)은 같은 옛 횟수를 함께 갖는다. 옛 횟수에는 어느 판인지 가릴 표시가 없어서, 기기별 값을 더하면 같은 판을 두 번 센다. 큰 값을 쓰면 두 번 세지 않는다. 대신 세션을 남기기 전에 서로 다른 기기에서 **따로** 친 판은 덜 셀 수 있다. 옛 기록에만 해당하는 작은 손실이라 받아들인다. 세션을 남긴 뒤의 판은 세션 `id`로 정확히 센다.
- 지금 localStorage의 진도·종합 테스트 기록은 「최고 기록」을 보관하는 용도로 남긴다. 최고 기록은 큰 쪽으로 합쳐도 맞기 때문이다.

이 변경은 동기화가 없어도 백업 가져오기를 더 정확하게 만든다. 그래서 동기화보다 먼저, 따로 PR로 넣는다 (§7 S1).

### 4.4 설정

설정은 기록과 달리 늘기만 하는 값이 아니라 바뀌는 값이다. 그래서 **항목마다 따로**, 마지막에 바꾼 기기의 값을 따른다 (last-writer-wins).

| 항목 | 지금 키 | 맞추는가 |
|---|---|---|
| 전체 해금 `unlockAll` · 도움말 대기 `helpIdleMs` · 한자 채점 `requireKanji` · 속도 단위 `speedUnit` | `twiper.settings.v1` | 맞춘다 |
| 화면 언어 `language` | 같음 | 맞춘다. `auto`(기기 언어를 따름)도 하나의 값으로 맞춘다. 한 기기에서 English를 고르면 모든 기기가 영어가 되고, 「기기 언어」로 돌리면 기기마다 자기 언어로 돌아간다 |
| 튜토리얼·시험 규칙을 봤는지 (`twiper.onboarded`, `twiper.examRules.seen`) | 따로 | **맞추지 않는다.** 새 기기에서는 키보드 준비부터 안내하는 것이 맞다 |

```ts
/** 항목마다 값과, 그 값을 정한 때 */
type StampedSettings = {
  readonly [K in keyof Settings]?: { readonly value: Settings[K]; readonly stamp: Stamp };
};
interface Stamp {
  readonly at: number;        // 바꾼 때 (ms). 아래 규칙으로 정한다
  readonly deviceId: string;  // at이 같을 때 이긴 쪽을 정한다
}
```

- **저장:** `twiper.settings.v1`의 모양은 그대로 두고(지금 읽는 코드가 바뀌지 않게), 항목별 `Stamp`만 `twiper.settings.stamps.v1`에 따로 둔다.
- **바꿀 때:** 설정 화면에서 항목을 바꿀 때만 그 항목의 `Stamp`를 새로 찍는다. `at = max(지금 시각, 이 기기가 본 가장 늦은 at + 1)`이다. 시계가 늦은 기기라도 남의 값을 본 뒤에 바꾸면 그 값을 이긴다.
- **합칠 때:** 항목마다 `at`이 큰 쪽, 같으면 `deviceId`가 큰 쪽. 순서·중복과 무관하므로 모든 기기가 같은 값에 이른다.
- **처음 켤 때:** `Stamp`가 없는 항목은 가장 약한 값으로 친다. 동기화가 생기기 전에 바꾼 설정에도 `Stamp`가 없으므로, 켜는 방법에 따라 나눈다.
  - **「동기화 켜기」로 공간을 새로 만들 때:** 이 기기의 지금 설정 **모든 항목(기본값 포함)**에 `Stamp`를 찍어 올린다. 그래서 공간에는 늘 다섯 항목이 모두 있고, 들어오는 기기는 기본값까지 공간과 같아진다.
  - **「코드 입력」으로 들어올 때:** 합치기 전에 **이 기기에 남아 있던 `Stamp`를 모두 지운다** (예전에 다른 공간에 있던 기기라도). 지금 설정에는 새로 찍지 않는다. 그래서 **들어온 기기는 모든 항목에서 공간 설정을 따른다.** 들어온 뒤에 바꾼 항목부터 공간에 올라간다.
- **적용:** 받은 설정이 지금과 다르면 저장하고 바로 반영한다. 언어는 그 자리에서 바뀐다(지금 설정 화면과 같은 길). 연습 중에는 동기화하지 않으므로 치는 도중에 바뀌지 않는다.
- 백업 파일에는 지금처럼 설정을 넣지 않는다.

### 4.5 주고받는 순서

```
동기화 한 번 =
  1. 받기  GET  /api/sync/{spaceId}/batches?after={lastSeq}   (50개씩, 끝까지)
           → 풀고(복호화·압축 해제) 차례로 합친다 → lastSeq를 받은 것의 마지막 번호로
  2. 올리기 POST /api/sync/{spaceId}/batches                   (아래 「올릴 때」일 때만)
           → 성공하면 올린 만큼 outbox에서 지운다
```

- **올릴 때:** ① 동기화를 처음 켤 때는 outbox가 비어 있어도 한 번 올린다. 시도·세션 기록이 없고 진도·종합 테스트 기록·`legacyPlays`·설정만 있는 기기도 있기 때문이다. ② 그 뒤로는 outbox가 비어 있지 않거나, 지난번에 올린 뒤 설정을 바꿨을 때 올린다.
- **언제:** 앱을 열 때, 한 판을 끝냈을 때, 앱이 다시 앞으로 왔을 때(`visibilitychange`), 「지금 동기화」를 눌렀을 때. 30초 안에는 다시 하지 않는다. 연습 중에는 하지 않는다 (입력 중 화면이 바뀌면 안 된다).
- **실패하면:** outbox가 남아 있으므로 다음 기회에 다시 올린다. 같은 묶음을 두 번 올려도 합치기가 중복을 없앤다. 화면에는 「마지막 동기화 n분 전」만 보이고, 연속 실패할 때만 알린다.
- 자기가 올린 묶음도 다시 받는다. 합쳐도 바뀌는 것이 없으니 따로 걸러 내지 않는다.

### 4.6 서버

지금 배포처와 같은 Vercel에 둔다. API 여섯 개(Functions)와 Postgres 테이블 두 개면 된다.

```
POST   /api/sync/{spaceId}/batches          본문 { deviceId, iv, data } → { seq }
GET    /api/sync/{spaceId}/batches?after=n  → [{ seq, deviceId, iv, data, at }]
POST   /api/sync/{spaceId}/compact/start    본문 { upTo }          → { compactionId }  압축 임대. 공간마다 하나만
POST   /api/sync/{spaceId}/batches          + 헤더 Compaction-Id     스냅샷 조각. 끝내기 전까지 받기(GET)에 보이지 않는다
POST   /api/sync/{spaceId}/compact/finish   본문 { compactionId }  → 조각을 보이게 하고 upTo 이하를 지운다 (한 트랜잭션)
POST   /api/sync/{spaceId}/compact/abort    본문 { compactionId }  → 그 임대의 조각만 지우고 임대를 푼다
DELETE /api/sync/{spaceId}                  묶음을 모두 지우고, 공간에 「지움」 표시를 남긴다
모두   Authorization: Bearer base64url(authKey)
```

```sql
create table space (
  id         bytea primary key,           -- spaceId
  auth_hash  bytea not null,              -- SHA-256(authKey)
  bytes      bigint not null default 0,   -- 쌓인 암호문 크기 (한도 확인용)
  created_at timestamptz not null default now(),
  used_at    timestamptz not null default now(),
  deleted_at timestamptz,                 -- 「서버의 기록 지우기」 표시. 행은 지우지 않는다
  compaction_id    text,                  -- 진행 중인 압축 임대 (없으면 null)
  compaction_up_to bigint,
  compaction_at    timestamptz            -- 임대의 마지막 활동 시각
);
create table batch (
  space_id   bytea not null references space(id) on delete cascade,
  seq        bigint generated always as identity,
  device_id  text not null,
  iv         bytea not null,
  data       bytea not null,
  compaction_id text,                     -- 끝나지 않은 스냅샷 조각이면 그 임대 id, 보통 묶음과 끝난 스냅샷은 null
  at         timestamptz not null default now(),
  primary key (space_id, seq)
);
```

- 공간은 처음 올리는 요청이 만든다. 이미 있는 공간이면 `auth_hash`가 맞아야 한다.
- **번호(`seq`)는 커밋 순서대로.** 동시에 온 두 요청이 1·2번을 받고 2번이 먼저 커밋되면, 그사이 받은 기기는 `lastSeq = 2`로 올라가 1번을 영영 놓친다. 그래서 올리기 트랜잭션은 먼저 그 공간의 행을 잠그고(`select id from space where id = $1 for update`), 커밋할 때까지 쥔다. 같은 공간에 대한 쓰기는 한 줄로 서므로 번호 순서와 커밋 순서가 같다. 공간마다 기기가 몇 대뿐이라 기다림은 무시할 만하다.
- **지운 공간:** 「서버의 기록 지우기」는 묶음을 모두 지우고 `deleted_at`을 남긴다. 행과 `auth_hash`는 남겨, 지운 뒤 같은 코드로 오는 요청(올리지 못한 outbox가 남은 기기 포함)을 모두 `410 Gone`으로 거절한다. 그래서 같은 코드로 공간이 되살아나지 않는다. `410`을 받은 기기는 그 기기의 동기화를 끄고 「다른 기기에서 서버의 기록을 지웠어요. 다시 켜려면 새 코드를 만드세요」라고 알린다. 모든 기기에서 동기화가 끊긴다는 화면 안내(§4.7)는 이 규칙에서 나온다.
- **압축(compact):** 묶음이 쌓이면(예: 200개, 또는 공간이 한도의 절반인 10MB) 모든 묶음을 `upTo`번까지 받은 기기 하나가 압축한다.
  1. `compact/start { upTo }`로 **임대**를 받는다. 공간마다 임대는 하나뿐이다. 다른 임대가 살아 있으면 거절하므로 두 기기가 동시에 압축하지 않는다. 15분 동안 활동이 없는 임대는 버려진 것으로 보고, 다음 `start`가 그 조각을 지운 뒤 새 임대를 준다.
  2. 합친 전체를 요청 한도 안의 **스냅샷 조각 여러 개**로 나눠 `Compaction-Id`를 붙여 올린다. 조각은 `compaction_id`가 붙은 채 저장되어 받기(GET)에 보이지 않는다.
  3. 다 올라가면 `compact/finish`가 한 트랜잭션으로 조각의 `compaction_id`를 지워 보이게 하고 `upTo` 이하를 지운다. **옛 묶음은 스냅샷이 다 올라가기 전에는 지우지 않는다.**
  - **끊겼을 때:** 기기는 진행 중인 `compactionId`를 localStorage에 적어 둔다. 앱을 다시 열면 이어 올리지 않고 `compact/abort`로 그 임대의 조각만 지운 뒤 처음부터 다시 한다. 끝나지 않은 조각과 끝난 스냅샷은 `compaction_id`가 있느냐로 가린다.
  - **한도:** 끝나지 않은 조각은 공간 한도를 잠시 넘어도 받되, 조각의 합은 공간 한도(20MB)를 넘지 못한다. 그래서 공간은 많아야 40MB이고, 임대가 하나뿐이라 여러 압축이 이 여유를 나눠 먹지 않는다. 스냅샷은 합친 기록이라 옛 묶음 합보다 크지 않다.
  - 조각이 숨어 있는 동안 받은 기기는 옛 묶음을 그대로 받으므로 빠뜨리는 것이 없다. 아직 올리지 못한 기기의 기록은 그 기기의 outbox에 남아 있으므로, 나중에 올리면 된다. 합치기가 합집합이라 스냅샷과 늦게 온 묶음의 순서는 상관없다.
- **한도:** 요청당 512KB, 공간당 20MB, IP와 공간마다 분당 요청 수 제한. 1년 동안 쓰지 않은 공간은 지운다고 화면과 안내문에 밝힌다.
- **크기 어림:** 시도 기록 한 줄은 JSON으로 0.5–1KB, gzip을 거치면 그 1/3 안팎이다. 하루 100줄씩 1년을 쳐도 압축 후 10MB 안쪽이다. 구현할 때 실제 기록으로 다시 잰다.
- 서버가 아는 것: spaceId, 기기 ULID, 묶음 크기와 시각, 요청 IP(접속 기록). 연습 내용·글자·속도는 모른다.

| 방식 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 백업 파일 (지금) | 서버가 없다. 이미 있다 | 손으로 해야 하고, 늘 최신은 아니다 | **유지.** 기본 수단 |

| Firebase (Firestore + Auth) | 오프라인 캐시와 실시간 반영이 들어 있다 | SDK가 무거워 첫 화면 번들 요구(§3-6)와 맞지 않는다. 계정이 필요하고, 데이터가 평문으로 남는다 | 제외 |
| Supabase (Postgres + Auth) | 표준 SQL, 행 단위 권한 | 계정이 필요하다. 무료 플랜은 오래 쓰지 않으면 프로젝트가 멈춘다 | 계정 방식으로 갈 때의 후보 |
| **Vercel Functions + Postgres + 동기화 코드 + 종단 간 암호화** | 지금 배포처와 같다. 계정·개인정보가 없다. 서버는 암호문만 쌓는다. 합치기는 이미 있는 백업 규칙을 다시 쓴다 | 코드를 잃으면 서버 기록을 되찾을 수 없다. 서버를 직접 운영한다 | **추천** |

계정(Sign in with Apple, 패스키)은 나중에 더할 수 있다. 계정이 할 일은 「이 사용자의 동기화 코드를 안전하게 보관하는 것」뿐이므로, 위 구조를 바꾸지 않고 얹을 수 있다.

| 3 | 기기 시계가 틀림 | 기록 합치기는 시각에 기대지 않는다 (`id` 합집합과 단조 규칙). 설정만 시각을 쓰는데, 남의 값을 본 뒤에는 그보다 늦게 찍으므로(§4.4) 시계가 늦은 기기의 변경이 묻히지 않는다. 시계가 크게 앞선 기기의 값은 다른 기기가 다시 바꿀 때까지 이긴다 |
| 4 | 횟수가 두 번 더해짐 | §4.3대로 세션 수와, 기기별 `legacyPlays` 가운데 큰 값으로만 센다. 백업 가져오기도 같은 규칙을 따른다 |
| 5 | 서버 남용·비용 | 요청·공간 크기 한도와 속도 제한을 둔다. 1년 동안 쓰지 않은 공간은 지운다 |
| 6 | 저장 형식이 바뀜 | 묶음에 `version`을 둔다. 모르는 필드는 보존하고, 더 높은 버전은 건너뛰며 업데이트를 권한다 |
| 7 | 나중에 기록 지우기 기능을 넣음 | 지금 규칙은 늘기만 하는 기록을 전제로 한다. 지우기를 넣을 때는 지운 표시(tombstone)를 함께 동기화해야 한다. 그때 이 문서를 고친다 |
| 8 | 개인정보 안내 | 서버에 무엇이 남는지(§4.6 마지막 줄)를 설정과 README에 밝힌다. 내용은 암호문이지만 접속 기록은 남는다 |

| S3 | 서버 API 여섯 개 + Postgres + 한도·압축 임대 | 잘못된 authKey·큰 요청·잦은 요청을 막는 테스트, 압축 뒤에도 수렴 |
| S4 | `/lab/sync` 시안 → 설정 「기기 간 동기화」, ko·ja·en | 사용자가 시안을 확인한다 |
| S5 | 화면 흐름 테스트: 브라우저 두 개가 같은 코드로 기록과 설정을 주고받고(한쪽에서 속도 단위를 바꾸면 다른 쪽도 바뀐다), 오프라인에서 친 기록이 온라인이 되면 올라간다 | CI에서 통과 |
